TL;DR

  • Jr handles real Mac outages autonomously — alerts you, runs the recovery dance when Mac comes back, replays any queued writes for your review.
  • You'll get a daily 09:00 BRT digest while travel mode is active — "all systems green / here's what happened."
  • Tell Jr about planned shutdowns (e.g. UPS battery swap) so it suppresses false alarms.
  • Writes you ask for during an outage are QUEUED, not live — Jr replays them to Mac for your approval on recovery.

Telling Jr about a planned Mac shutdown (maintenance window)

If you need to shut Mac down deliberately (UPS battery swap, firmware, etc.), tell Jr in Telegram first so it doesn't fire alarms:

"Jr, I'm shutting Mac down at 14:00 for ~2h to swap UPS batteries."

Jr confirms + sets a maintenance window. During the window:

  • [PRIMARY DOWN] alerts: suppressed
  • Heartbeat-while-down pings: suppressed
  • Recovery dance: still fires silently on up-edge (validates everything came back clean)
  • On Mac return: single [MAINTENANCE COMPLETE] message instead of the alarm sequence
  • If queued writes exist on recovery: [MAINTENANCE REPLAY] message with count

If your shutdown takes longer than planned: "Jr, extend the maintenance window by another hour."

If Mac comes back early: "Jr, clear the maintenance window."

Critical caveats

⚠️ Writes are queued, not live

When you ask Jr to draft an email, create a calendar event, or create a Drive file during an outage, Jr does NOT directly call the Google API. Instead it appends the intent to jr_outage_log.jsonl. On recovery, the queue replays to Mac as jr_recovery_pending.jsonl which you review + approve.

Don't assume "Jr drafted the email, done." You still need to approve on recovery before it materializes. Jr will tell you the queued count in [RECOVERY COMPLETE].

⚠️ Inbound WhatsApp messages stranded during outage

If someone messages your WA number (+5511994917618) while Mac is down, those messages cache server-side at WhatsApp. They'll arrive when Mac is back. Jr has zero visibility into inbound WA during outage by design.

📷 Jr's media memory (v1.26)

When you send Jr a voice memo, it ALWAYS transcribes first then responds. When you send an image, Jr describes what it sees then responds. The transcript/description ends up in Jr's persistent memory. The audio/image binaries themselves don't persist (Phase 0d.4 multimodal, deferred).

Manual fallbacks (rarely needed)

If Jr itself dies (Hetzner outage, OAuth daemon crash, disk full, etc.) — extremely rare:

  • Hetzner outage: outside our control; restores naturally within hours typically
  • Verify Jr health from any Mac on Tailscale: ssh superclawman-jr 'systemctl list-timers openclaw-jr-*' — all timers should show recent LAST and upcoming NEXT
  • Verify OAuth daemons: ssh superclawman-jr 'systemctl --user list-timers openclaw-jr-*-refresh@paulo.timer'
  • Manually trigger watchdog: ssh superclawman-jr 'JR_TENANT_ID=paulo python3 /usr/local/lib/openclaw-jr/vps-watchdog.py'

If Mac stays offline beyond what's reasonable (e.g. >24h with no power coming back):

  • The recovery dance can't run until Mac returns. Jr keeps watching.
  • Workflow needs to wait. No emergency procedure required.
